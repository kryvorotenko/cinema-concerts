# DPC ЛР2: результати 2026-11-23

Середовище: Windows / Docker Desktop Linux container, CPython 3.14.8; host CPU AMD Ryzen 5 5600, **6 фізичних / 12 логічних ядер**. CPU quota Docker може зменшувати доступну паралельність. Дані: `A=120`, `τ=30`, `T=90`, `a=0`, `b=90`, `n=5 000 000`, midpoint (order 2), абсолютний допуск 0.02 проходу. Еталон `86491.98646508278`, похибка кожного режиму приблизно `1.78e-9`.

Кожна медіана ґрунтується на **трьох** вимірюваннях. Сирі трійки, повна точність і профіль — у [dpc-lr2-benchmark.json](dpc-lr2-benchmark.json). Час включає startup пулу, передавання параметрів/часткових сум, інтегрування, збирання, редукцію й shutdown; не включає HTTP. Профіль батьківського процесу: 0.699 с із 0.699 с в `calculate`, 0.698 с у shutdown/join (очікування worker-ів). Він не профілює обчислення всередині дітей. Гіпотеза: зменшення кількості частин з 4 до 1 на worker скоротить накладні витрати. Повтор без профайлера на тій самій задачі й точності дав 4-worker медіану **0.692 с замість 0.673 с**; гіпотеза не підтвердилася. Можливі причини — шум планувальника та кращий баланс коротших частин; цей профіль не дозволяє відділити їх від CPU quota.

Дослід спільної суми: 4 процеси, `n=10000`, Simpson, допуск 0.01. В одному запуску unsafe `29032.135227975723` проти еталона `86491.98646508278`; lock `86491.98646508278`, local sums `86491.98646508277`. Barrier гарантує, що всі 4 процеси читають спільний нуль до записів. Повтор локально теж показав lost update; конкретна unsafe сума змінюється через порядок записів, захищені варіанти збігаються з еталоном.

HTTP перевірка: Simpson/4, `n=10000`, 2 процеси → `value=86491.98646508277`, `reference=86491.98646508278`, `error≈1.46e-11`; без Bearer — 401, невалідний інтервал — 400.
