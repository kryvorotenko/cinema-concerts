## О2.1: як зберігається інваріант

`POST /v1/holds` в одній транзакції виконує

```sql
UPDATE seat_categories c SET available = c.available - K
WHERE c.id = :category AND c.sales_open AND c.available >= K AND <виконання ще продається>
RETURNING c.id
```

Перевірка й зміна — один оператор, тому між ними не може вклинитися інший запит: PostgreSQL бере блокування рядка
категорії, а після очікування перевіряє умову на вже оновлених даних. Якщо рядок не оновлено, відповідь — 409
(`not-enough-seats`, `sales-closed`, `performance-unavailable`) або 404. Рядок утримання вставляється в тій самій
транзакції, тому `available` і утримання змінюються разом або не змінюються.

Чому не інакше:

| Варіант | Чому не обрано |
|---|---|
| Локальний mutex у процесі | Не діє між `app-a` і `app-b`: один екземпляр не бачить іншого |
| `SELECT ... FOR UPDATE`, потім `UPDATE` | Працює, але це два звернення до бази й довший час тримання блокування |
| `SERIALIZABLE` з обмеженим повтором | Працює, але за гарячої категорії більшість запитів отримують помилку серіалізації й повторюються |
| Лічильник у Redis | Друге джерело правди: розходження з базою за збою між двома записами |

Умовний `UPDATE` — найкоротше блокування й один рядок як точка серіалізації; `CHECK (available >= 0)` у схемі
лишається останньою лінією захисту.

Для досліду є режим `INVARIANT_MODE=unprotected` (змінна вже є в `docker-compose.yml`): залишок читається окремим
`SELECT`, а потім записується обчислене значення. Це навмисно хибний варіант для порівняння, у штатному режимі
`protected` він не діє. Результат порівняння — в [results/web-lr2.md](../../results/web-lr2.md).

## О2.2: ключі ідемпотентності

Заголовок `Idempotency-Key` обов'язковий для `POST /v1/holds`: 1…255 видимих ASCII-символів без пропусків.

| Ситуація | Відповідь |
|---|---|
| Ключа немає, він порожній, задовгий або з пропуском | 400 `idempotency-key-required` / `idempotency-key-invalid` |
| Новий ключ | виконання, 201, відповідь збережено |
| Той самий ключ, те саме тіло | та сама відповідь (201, той самий `id`, `Location`, `ETag`) із заголовком `Idempotent-Replayed: true`; ефекту немає |
| Той самий ключ, інше тіло | 422 `idempotency-key-reused` |
| Перший запит із цим ключем ще виконується | 409 `request-in-progress` з `Retry-After: 1` |
| Ключ прострочений (понад 24 години) | запит вважається новим |

Порядок перевірок: автентифікація (401), потім ключ (400), потім тіло (400 не JSON, 422 хибні дані).

**Що зберігається.** Рядок `idempotency_keys` з первинним ключем `(user_id, key)`: операція (`POST /v1/holds`),
відбиток тіла, стан (`completed`), код і тіло відповіді, `Location`, `ETag`, `created_at`, `expires_at`.
Рядок записується **в тій самій транзакції**, що й ефект (зменшення `available`, утримання): або є обидва, або жодного.
Через це не буває ефекту без збереженої відповіді, і навпаки.

**Відбиток тіла** — SHA-256 від канонічного JSON (ключі відсортовано, без пробілів), тому порядок полів і пробіли
не впливають. Відбиток береться від розібраного й перевіреного тіла, а не від сирих байтів.

**Ключ належить користувачу.** Той самий рядок ключа в іншого користувача — незалежний ключ.

**Як відрізняється «ще виконується».** Транзакція на початку бере `pg_try_advisory_xact_lock` за хешем
`(користувач, ключ)`. Це блокування на рівні бази, тому воно діє між екземплярами. Якщо блокування вже тримає
чужа транзакція, повтор одразу отримує 409 замість очікування. Після її commit блокування знімається, а рядок ключа
вже видно: повтор отримує збережену відповідь. Через це стан «виконується» ніколи не лишається в таблиці після збою:
нічого не треба «розблоковувати» вручну. Хеш 64-бітний; колізія двох різних ключів дала б хибний 409, який клієнт
просто повторить.

**Що не зберігається.** Невдалі відповіді (409, 422, 404) у таблицю не потрапляють: транзакція відкочується, повтор
обчислюється заново, і, якщо місця з'явилися, завершується успішно. Зберігаються лише відповіді 201.

**Збережена відповідь — знімок.** Повтор повертає утримання таким, яким воно було на момент створення (`status: held`),
навіть якщо воно вже `expired`; поточний стан дає `GET /v1/holds/{id}`.

**Очищення.** Фонове завдання кожного екземпляра раз на `IDEMPOTENCY_PURGE_S` (60 с) видаляє прострочені ключі
порціями по `IDEMPOTENCY_PURGE_BATCH` (500) з `FOR UPDATE SKIP LOCKED`, у короткій транзакції на порцію. Прострочений
ключ, що трапився запиту раніше за завдання, видаляється й замінюється новим. Термін життя — `IDEMPOTENCY_TTL_S` (24 години).

## О2.3: відмова `after_commit_before_response`

`fault("after_commit_before_response")` стоїть у `create_hold` одразу після виходу з транзакції (commit виконано),
перед надсиланням відповіді. Якщо файл `/faults/after_commit_before_response` існує й `FAULTS=on`, процес його
видаляє, пише `fault.hit` і завершується без очищення. Docker перезапускає його (`restart: unless-stopped`).

Клієнт не отримує відповіді, хоча утримання створено. Повтор із тим самим ключем (на інший екземпляр або на той самий
після перезапуску) читає збережений рядок і повертає ту саму відповідь: місця зайнято один раз.

## О2.4: повтор на клієнті

`callIdempotent` в `web/client/api.js` створює ключ один раз на дію користувача (`crypto.randomUUID()`) і надсилає
його в усіх спробах.

- Повторюються: немає відповіді (мережа), 502, 504, 503 і 409 `request-in-progress`. Остаточні помилки
  (404, 409 `not-enough-seats`, 422) не повторюються.
- Затримка: експоненційне зростання з повним джитером, `random(0, min(cap, base · 2^(n-1)))`, `base` 400 мс,
  `cap` 5 с; не раніше за `Retry-After`.
- Межі: 5 спроб і 20 с загалом.
- Якщо відповіді так і не було (мережа, 502, 504, 409 «виконується»), результат **невідомий**: клієнт показує це й
  пропонує «Повторити з тим самим ключем» (утримання не задвоїться). 503 повідомляється як 503: робота не починалась.

## Інші зміни

- 503 `overloaded` з `Retry-After: 1`, якщо всі з'єднання пулу зайняті довше `POOL_TIMEOUT_S` (раніше це був би 500).
- CORS: `Idempotent-Replayed` додано до `expose_headers`; `Idempotency-Key` уже був у дозволених.
- Нові змінні: `IDEMPOTENCY_TTL_S`, `IDEMPOTENCY_PURGE_S`, `IDEMPOTENCY_PURGE_BATCH`.

## Для ЛР3–ЛР4

- Ключі ідемпотентності прив'язані до `user_id` із `current_user`; після ЛР3 нічого не змінюється, тільки джерело користувача.
- Оплата (ЛР4) має власну таблицю `operations` із `UNIQUE (user_id, idempotency_key)`. `idempotency_keys` призначена
  для операцій, що відповідають одразу; зберігати там довгі операції не треба. Колонка `operation` відрізняє
  використання одного ключа в різних маршрутах (422).
- Міграція ЛР2 — `021`, у діапазоні `020–029` за пропозицією з WEB-LR1.
