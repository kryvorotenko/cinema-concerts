## О6.1: зміна «лічильник → конкретні місця»

Було: категорія має `capacity` і `available`, утримання — кількість `seats`. Стало: кожне місце категорії — рядок
`seats` (ряд, номер), а утримання посідає конкретні місця через `booking_seats`.

| Таблиця | Зміна |
|---|---|
| `seats` | з `001`, була порожня; тепер по одному рядку на місце, `id = <категорія>:<ряд><номер>`, ряд називається `<назва категорії> <літера>`, у ряду 10 місць |
| `booking_seats(seat_id PK, booking_id)` | нова; первинний ключ `seat_id` гарантує, що місце тримає не більше одне активне утримання; `ON DELETE CASCADE` за `bookings` |
| тригер `bookings_release_seats` | за переходу утримання з `held`/`confirmed` у `expired`/`cancelled`/`refunded` видаляє його рядки в `booking_seats` |
| `feature_flags(name, enabled)` | нова; рядок `explicit-seats`, початково `false` |

`bookings.seats` і `seat_categories.available` лишаються: перший — кількість місць утримання, другий — лічильник для
швидкого умовного `UPDATE` з ЛР2. Місця додаються до лічильника, а не замінюють його. `available` змінюється так само,
як і раніше, у тій самій транзакції; після цього утримання отримує місця. Блокування рядка категорії, яке бере
умовний `UPDATE`, послідовно впорядковує всі утримання однієї категорії, тому два запити не можуть претендувати на
одне місце одночасно; первинний ключ `booking_seats` лишається останньою лінією захисту.

### Поведінка

| Запит | Прапорець off | Прапорець on |
|---|---|---|
| `POST /v1/holds {category_id, seats}` (клієнт попередньої версії) | 201, сервер сам призначає сусідні вільні місця одного ряду (якщо такого відрізка немає — перші вільні); відповідь без нових полів | те саме, у відповіді є `places` |
| `POST /v1/holds {category_id, seat_ids}` | 422 `seat-selection-disabled`, нічого не змінюється | 201 з обраними місцями |
| місце зайняте | — | 409 `seat-taken`, транзакцію скасовано повністю (`available` і місця без змін) |
| місце не з цієї категорії або невідоме | — | 422 `invalid-seat` |
| `seats` і `seat_ids` разом, жодного з них, порожній чи повторюваний `seat_ids` | 422 | 422 |
| `GET /v1/categories/{id}/seats` | 404 `feature-disabled` | схема місць із ознакою `free` |
| `GET /v1/features` | `{"explicit_seats": false}` | `{"explicit_seats": true}` |

Відбиток ключа ідемпотентності рахується без порожніх полів, тому запит клієнта попередньої версії має ті самі
відбиток і повтор, що й до ЛР6 (ключі, створені до оновлення, не ламаються).

### Порядок введення (expand → перехідний режим → backfill → перевірка → прапорець → contract)

| Крок | Дія | Команда | Чи можна повернутись |
|---|---|---|---|
| 1. Розширення | таблиці, тригер, прапорець `off` | `docker compose up -d --build` застосовує `023` | так: нічого не змінює для старого коду |
| 2. Перехідний режим | новий образ на `app-a` і `app-b`, прапорець `off`; нові утримання вже отримують місця | оновлення по черзі | так |
| 3. Заповнення | створити місця категорій порціями (`--batch`, типово 100) і призначити місця наявним утримань | `docker compose exec app-a python -m app.seats_admin backfill` | так: команда повторювана |
| 4. Перевірка | кількість місць = `capacity`; зайняті = `capacity − available`; активне утримання має рівно `seats` місць; завершені не тримають місць | `docker compose exec app-a python -m app.seats_admin check` | так |
| 5. Прапорець | нова поведінка для клієнтів | `docker compose exec postgres psql -U app -d app -c "UPDATE feature_flags SET enabled = true WHERE name = 'explicit-seats'"` | так, див. нижче |
| 6. Contract | прибирання старого | **не виконується** | — |

Нових обов'язкових стовпців у наявних таблицях немає (`NOT NULL` до заповнення не вводиться). Поки працює
екземпляр попередньої версії, він створює утримання без місць; тому крок 3 і 4 повторюють перед вмиканням прапорця,
а `check` показує, чи лишилися утримання без місць. Прапорець вмикають лише коли всі екземпляри нові.

Чому немає contract-кроку: `bookings.seats` і `seat_categories.available` використовують атомарний `UPDATE` з ЛР2,
відповіді API і перевірка квитка для DPC. Їх зараз використовують, тож за методичкою їх не видаляють.

### Повернення

Межа повернення — усі кроки 1–5; повернутись можна завжди, бо зміна лише додає.

| Що | Команда |
|---|---|
| вимкнути нову поведінку | `docker compose exec postgres psql -U app -d app -c "UPDATE feature_flags SET enabled = false WHERE name = 'explicit-seats'"` |
| повернути код ЛР3 | `git switch andrey-web-lab3` і `docker compose up -d --build` (потім `docker compose restart nginx`); міграцію `023` не скасовують |

Стан даних після повернення: усі утримання, створені новою версією, лишаються чинними; їхні рядки `booking_seats`
зберігаються й не заважають старому коду (він їх не читає). Коли такі утримання закінчуються, тригер сам звільняє місця.
Утримання, створені старим кодом після повернення, не мають місць; перед повторним вмиканням прапорця виконують
`backfill` і `check`. Видалення таблиць `booking_seats` чи `seats` було б не поверненням, а знищенням нових даних,
тому не виконується.

## О6.3: готовність і коректне завершення

Для сигналу `SIGTERM` (так зупиняє контейнер `docker compose stop`/`kill -s SIGTERM`):

1. `lifecycle.install_sigterm()` перехоплює сигнал і запускає завершення; прапорець готовності `/ready` → 503
   `draining` з `Retry-After: 1`. `/health` лишається 200 (процес живий).
2. Окремий механізм припинення нової роботи — `DrainGuard` (ASGI, у `lifecycle.py`): запит на будь-який маршрут,
   крім `/health`, `/ready`, `/metrics`, отримує 503 `shutting-down` з `Retry-After: 1` і `Connection: close`
   і не потрапляє в обробник. Прапорець `/ready` сам цього не робить: його лише читають перевірки.
3. Запити, що вже виконуються, не переривають. `DrainGuard` рахує їх; після `DRAIN_DELAY_S` (типово 2 с) процес чекає,
   поки лічильник дійде до нуля, але не довше `DRAIN_TIMEOUT_S` (типово 20 с).
4. Лише тоді сигнал передається uvicorn, який закриває порт, закінчує лишні з'єднання (`--timeout-graceful-shutdown 25`)
   і запускає завершення `lifespan` (фонові завдання скасовуються, пул закривається). `stop_grace_period` у Compose — 30 с.

Затримка `DRAIN_DELAY_S` потрібна, щоб nginx і перевірки встигли побачити 503, поки порт ще відкритий. Відповідь
`shutting-down` для `POST` nginx не повторює на іншому екземплярі (він не повторює вже надіслані `POST`), тож клієнт
отримує 503 з `Retry-After`; клієнт з ЛР2 (`callIdempotent`) повторює запит із тим самим ключем.

Утримання в обробнику підтверджується лише після `COMMIT` (відповідь надсилається після транзакції), тому
розпочатий запит або фіксується повністю, або ні. Частини завдання про worker (ack після commit) і gateway (закриття
WebSocket кодом 1012) стосуються ЛР4 і ЛР5; вони використовують ті самі `lifecycle.start_draining()` і `is_draining()`.

Для перевірки є точка паузи `slow_request` у `faults.py` (`pause`): файл у каталозі відмов вмикає однократну
затримку `FAULT_PAUSE_S` усередині транзакції створення утримання.

## Змінні й команди

| Змінна | Типово | Призначення |
|---|---|---|
| `DRAIN_DELAY_S` | 2 | скільки секунд після SIGTERM порт ще відповідає 503 |
| `DRAIN_TIMEOUT_S` | 20 | скільки чекати на завершення розпочатих запитів |
| `FAULT_PAUSE_S` | 3 | тривалість паузи `slow_request` (лише `FAULTS=on`) |

Команди `python -m app.seats_admin backfill [--batch N]` і `python -m app.seats_admin check` виконують із каталогу
`web/server` або всередині контейнера `app-a`.
