# Робота команди та агентів

Цей документ допомагає кожному учаснику почати свою частину спільного C01.
Розподіл номерів лабораторних — у [TEAM.md](knowledge/TEAM.md); імена учасників
команда ще не записала. Людина може доручити своєму агенту конкретну ЛР або пункт.

## Перший запуск

1. Клонуйте репозиторій або оновіть свою робочу гілку: `git pull`.
2. З кореня проєкту скопіюйте `.env.example` до `.env`: `cp .env.example .env`
   або PowerShell `Copy-Item .env.example .env`. Не публікуйте `.env`.
3. Запустіть Docker Desktop чи Docker Engine. Виконайте
   `docker compose up -d --wait postgres broker`, потім
   `docker compose run --rm migrate` і `docker compose run --rm broker-init`.
4. Виконайте `python experiments/check_foundation.py`. Команда перевіряє
   конфігурацію, шляхи й домовленості каркаса; це не перевірка лабораторних.
5. Прочитайте [контракт Дня 1](contracts/README.md), а для своєї ЛР —
   [Web](knowledge/WEB.md) або [DPC](knowledge/DPC.md).

Детальні команди для всього каркаса та профілів — у [кореневому README](../README.md).
Web-клієнт і DPC-клієнт запускаються окремо, як там зазначено. Немає потреби
запускати всі профілі одночасно. Для локальних експериментів використовуйте
власну копію БД або ізольовані тестові дані.

## Що сказати агенту

Учасник може відкрити проєкт в інструменті, який читає `AGENTS.md`, і дати
конкретне завдання, наприклад:

> Прочитай AGENTS.md, docs/contracts/README.md і відповідний розділ
> docs/knowledge/WEB.md або DPC.md. Працюй над [курс, номер ЛР і пункти].
> Збережи сумісність спільних інтерфейсів, перевір результат і онови README.

Якщо інструмент не читає `AGENTS.md` автоматично, вкажіть цей файл явно.
Номери пунктів та розділ `Ядро` беріть з пам'яті курсу; необов'язкові пункти
обираються окремо. Агенту не потрібно щоразу перечитувати повні PDF.

## Де працювати

| Зона | Основні файли | Спільна межа |
|---|---|---|
| Web ЛР1–3, 6 | `web/server/app/`, `web/client/`, майбутній `web/openapi.yaml` | `bookings`, категорії та квитки; зміни схеми — нова міграція |
| Web ЛР4–5 | `web/server/app/`, `web/tools/external-sim/`, `config/` | outbox, domain-events, notifications, авторизація шлюзів |
| DPC ЛР1–3, 6 | `dpc/api/app/`, `dpc/coordinator/`, майбутній `dpc/openapi.yaml` | Web ticket API, sector/effect, резерви, покоління та історія |
| DPC ЛР4–5 | `dpc/spark/jobs/`, `dpc/tools/generator/`, `experiments/` | `ticket-telemetry`, Parquet, schema подій, batch reference |

Ці шляхи — орієнтири, не заборона змінювати інші файли. Код у шаблонах має
позначки TODO: наявність сервісу не означає, що відповідну ЛР виконано.

## Одночасні зміни

- Перед роботою перевірте `git status` і наявні зміни. Не перезаписуйте чужу
  незавершену роботу. Використовуйте власні гілки за домовленістю команди;
  перед злиттям оновіть гілку й перевірте спільні файли.
- Спільні файли — `docker-compose.yml`, `config/project.env`, `migrations/`,
  `docs/contracts/`, OpenAPI й схеми подій. Узгоджуйте зміни їхніх контрактів
  з учасниками, на яких вони впливають. Не перейменовуйте топіки чи ID мовчки.
- `001_shared_foundation.sql` вже застосовується: не редагуйте її. Додавайте
  новий файл `NNN_назва.sql`. Паралельні гілки можуть вибрати один номер —
  перед застосуванням і злиттям перевірте його унікальність та узгодьте порядок.
  Якщо файл вже застосовано, виправлення оформлюйте новою міграцією.
- Фіксуйте у README виконані критерії окремо для Web/DPC, команди відтворення,
  фактичні результати й обмеження. Зберігайте експерименти у `experiments/`,
  невеликі результати — у `results/`, не додавайте секрети й великі датасети.
- При передачі іншому учаснику назвіть гілку/коміт, змінені API та схему,
  необхідні міграції, виконані перевірки та невирішені залежності.

## Що вже узгоджено

Один PostgreSQL і один Kafka; `screenings.id` є `performance_id`.
Web змінює продажі та випускає квитки. DPC веде заповненість секторів та
погашає квиток за `ticket_id`. Топік `ticket-telemetry` — обране ім'я потоку
`scans` із картки C01; його формат у [контракті](contracts/README.md).
Таблиця `seats` — заготовка для Web ЛР6, а не готовий вибір місць.
Початкова міграція не реалізує операції, інваріанти за конкурентності чи fencing.
