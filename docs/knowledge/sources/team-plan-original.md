Для теми **C01 (Кінотеатри й концерти)** спільним ресурсом у PostgreSQL є **місце на конкретний сеанс або концерт** (`screening_id, seat_id`). Головний бізнес-інваріант обох курсів: одне місце не може бути одночасно заброньоване чи продане двічі — ні користувачем через сайт (**Web**), ні потоком замовлень із кас чи партнерських агрегаторів (**DPC**).

## 2. Розподіл роботи на 4 людини (без взаємного блокування)

Щоб ніхто не простоював в очікуванні чужої інфраструктури, команда ділиться за **вертикальними технічними доменами**, а спільна інфраструктура (Kafka, Spark, Postgres) піднімається наперед.

### День 1: Спільна точка синхронізації (2–3 години разом)

Перед стартом кодингу всі четверо фіксують у репозиторії один файл міграцій SQL та константи:

* **Таблиці БД**: `users`, `events`, `screenings`, `seats`, `bookings` (з полями `status`, `hold_expires_at`, `fencing_token`), `outbox`, `processed_effects`.
* **Топіки Kafka**: `domain-events` (для Web ЛР4), `notifications` (для Web ЛР5), `ticket-telemetry` (для DPC ЛР5).
* **Порти сервісів** у єдиному `docker-compose.yml`.

---

### Закріплення зон відповідальності

#### Людина 1 — Web Core & Zero-Downtime Lead

* **Зона**: **Web ЛР1 (3) $\rightarrow$ Web ЛР2 (5) $\rightarrow$ Web ЛР3 (4) $\rightarrow$ Web ЛР6 (6)** *(сумарна складність: 18)*
* **Що робить**: Весь синхронний API кінотеатру/концертів, базовий фронтенд (афіша, інтерактивна сітка місць у залі, особистий кабінет, адмінка `staff`), захист від подвійного бронювання місця в БД, аутентифікація/RBAC та фінальна zero-downtime міграція схеми під навантаженням.
* **Чому не блокує інших**: У перший день створює базовий Compose з `postgres` і `nginx`, далі працює автономно у своєму сервісі `web-app`.

#### Людина 2 — Kafka, Async & Real-time Lead

* **Зона**: **Підняття Kafka + `external-sim` $\rightarrow$ Web ЛР4 (7) $\rightarrow$ Web ЛР5 (7)** *(сумарна складність: ~17)*
* **Що робить**:
1. На старті додає в `docker-compose.yml` брокер **Kafka (KRaft)** (щоб не блокувати Людину 3 і Людину 4) та пише мок-сервіс `external-sim` (імітація еквайрингу та генератора QR-квитків).
2. Реалізує Transactional Outbox (`publisher` через `FOR UPDATE SKIP LOCKED`), фоновий `worker` та асинхронний статус оплати `202 Accepted` (Web ЛР4).
3. Піднімає два WebSocket-шлюзи (`gateway-a/b`) з одноразовими квитками та стрічкою сповіщень з курсором (Web ЛР5).


* **Чому не блокує інших**: Виносить Kafka на самий початок, завдяки чому DPC-розробники отримують брокер задовго до того, як дістануться до стрімінгу.

#### Людина 3 — DPC High-Load, Ray & Coordination Lead

* **Зона**: **DPC ЛР1 (5) $\rightarrow$ DPC ЛР2 (4) $\rightarrow$ DPC ЛР3 (7) $\rightarrow$ DPC ЛР6 (8)** *(сумарна складність: 24)*
* **Що робить**:
1. Пише сервіс `dpc-api` для масового прийому касових/партнерських бронювань з обмеженою чергою, бекпрешером (`429`/`503`) і тим самим правилом блокування місця в PostgreSQL, що й у Людини 1 (DPC ЛР1).
2. Додає `POST /v1/compute` із багатопроцесним чисельним інтегруванням моделі попиту на квитки та замірами $S_p, E_p$ (DPC ЛР2).
3. Переносить обробку бронювань на кластер **Ray** (`ray-head`, `ray-worker`) із таблицею ефектів у БД (DPC ЛР3).
4. На фіналі додає **etcd** та `coordinator-a/b` (TTL $\le$ 5 с), який автоматично скасовує прострочені неоплачені броні місць із перевіркою `fencing_token` у Postgres (DPC ЛР6).


* **Чому не блокує інших**: Працює в окремому сервісі `dpc-api` і власних контейнерах `ray` та `etcd`, перетинаючись з іншими лише через узгоджену в День 1 таблицю `bookings`.

#### Людина 4 — Big Data & Streaming Analytics Lead

* **Зона**: **Генератор Parquet + Spark Cluster $\rightarrow$ DPC ЛР4 (8) $\rightarrow$ DPC ЛР5 (9)** *(сумарна складність: ~20)*
* **Що робить**:
1. Поки інші пишуть перші API, піднімає кластер **Spark** (`spark-master`, `spark-worker-1/2`) у Compose та пише генератор історичних продажів квитків у форматі **Parquet** (зі штучним перекосом: 80% квитків припадає на один великий концерт).
2. Реалізує пакетну аналітику виручки й заповнюваності залів (`/v1/reports/main/refresh`), звірку з еталоном і усунення data skew через salting (DPC ЛР4).
3. Підключає **Spark Structured Streaming** до топіка `ticket-telemetry` у Kafka (який вже підняла Людина 2) для розрахунку живої панелі продажів і проходів через турнікети з watermark та checkpointing (DPC ЛР5).


* **Чому не блокує інших**: Повністю незалежна від готовності Web-частини та Ray.
