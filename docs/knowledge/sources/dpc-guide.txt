1 Вступ
1.1 Як проходить робота
1. Команда. Проєкт виконує команда з 2–4 осіб. Кожне завдання виконують один раз на
проєкт; роботу команда розподіляє сама. README вказує внесок кожного учасника.
2. Вибір теми. До ЛР1 команда обирає спільну тему C01–C30 або тему курсу D01–D10. У
межах групи теми не повторюються. Власну предметну область (domain) можна запро-
понувати, якщо для неї можна заповнити всі поля картки; її погоджує викладач.
3. Завдання й картка. Пункти лабораторних робіт однакові для всіх тем ( розд. 2). Картка
(розд. 3) описує предметну область і містить пропоновані дані, маршрути, сценарії та ва-
ріанти розвитку системи. Реалізуйте можливості, потрібні для ядра й вибраних пунктів
лабораторних робіт. Структуру даних і предметні маршрути можна адаптувати, зберіга-
ючи інваріанти та узгоджений контракт API.
4. Шість робіт. Кожна ЛР розвиває той самий проєкт. Позначка Ядро виділяє обов’язкові
пункти. Решта основних пунктів — бажане поглиблення, а додаткові пункти пропону-
ють подальші досліди й можливості. Команда обирає їх відповідно до бажаної глибини
роботи. Вимоги вже виконаних пунктів залишаються чинними. Якщо розширення вико-
ристовує інший пункт, цю залежність зазначено в завданні.
5. Захист. Готовий проєкт захищається цілком після завершення роботи над усіма шістьма
ЛР: ядром і вибраними розширеннями. Команда запускає систему й демонструє резуль-
тати за README. Викладач перевіряє проєкт своїм засобом check, переглядає код, ре-
зультати дослідів і ставить запитання всім учасникам. Для спільного проєкту двох курсів
проводиться один захист після готовності обох частин.

1.4 Технології
У завданнях використано Ray, Spark, Kafka, etcd, PostgreSQL і Docker Compose. У лекціях на
їхньому прикладі пояснюються принципи паралельних і розподілених обчислень. Можна ви-
користовувати інші технології, що забезпечують потрібні механізми, наприклад Dask замість
Ray, Flink замість Spark Structured Streaming або ZooKeeper замість etcd. Обрані технології за-
значте в README та поясніть, як вони забезпечують виконання вимог.
У додаткових матеріалах, які надаються разом із курсом, є каркаси програм, конфігура-
ції середовища, генератори даних та засоби проведення дослідів. Інструкції з використання
наведено у відповідних README. Надані компоненти можна адаптувати до своєї теми або роз-
робити власні. Під час захисту команда пояснює їхню роботу й демонструє виконання вимог.
Використані готові рішення та власний внесок зазначають у README.
1.5 Формат часу подій
Час події задавайте в UTC: рядком дати й часу у форматі ISO 8601 із позначкою Z або цілим чи-
слом мілісекунд від 1970-01-01T00:00:00Z. Обраний формат зафіксуйте в контракті та узгодь-
те між генератором, обробником і еталонним розрахунком. Зберігайте точність до мілісекунд.

1.6 Розрахунок ЛР2
Основний метод — чисельне інтегрування функції з картки (метод середніх прямокутників,
метод трапецій або метод Сімпсона). Еталонне значення визначеного інтеграла обчислюють
за наведеною в картці первісною; кількість частин n задає навантаження. Інші методи з кар-
тки — за вибором команди. У картках використано скорочення ОДР для звичайного диферен-
ціального рівняння (ordinary differential equation, ODE).
1.7 Що має бути в результаті
Репозиторій містить сервіс api з чергою й пулом обробників, клієнт або сценарії звернення
до API, міграції, контракт openapi.yaml, паралельний розрахунок, задачі Ray та приймач ефе-
ктів, звіт Spark з незалежним еталоном, потокову задачу, координатори й перевірку поколі-
ння на ресурсі. Для дослідів підготовлено дані та засоби їх відтворення. Решта можливостей
визначається вибраними пунктами.
1.8 Керовані відмови
Керований дослід відтворює відмову в проміжку між діями, які не можна виконати атомар-
но. Для відмов у коді використовуйте протокол комплекту: FAULTS=on дозволяє режим, файл
/faults/<name> вмикає відмову в названому місці. Процес забирає прапорець, записує fault.
hit і негайно аварійно завершується без штатного завершення роботи. Один прапорець має
спричинити одну відмову; це має враховувати наявність кількох процесів. Зупинку контейне-
ра й паузу координатора відтворюють окремими діями.
README називає місце відмови, команду її ввімкнення, запис журналу та спосіб віднови-
ти початковий стан. Таблиця нижче описує можливі досліди; виконують ті, що належать до
вибраних пунктів.

1.9 Репозиторій і README
Репозиторій містить код сервісів, клієнта й генераторів (або опис даних для генератора з дода-
ткових матеріалів), міграції, опис API, файли запуску контейнерів. README описує проєкт так,
щоб людина, яка бачить його вперше, зрозуміла, з яких технологій і компонентів він складає-
ться, що з чим взаємодіє і що відбувається під час роботи. Схеми вітаються. README містить
такі розділи:
1. Курс і тема. Назва курсу, ідентифікатор і назва теми, склад команди.
2. Проєкт. Призначення платформи, спільний ресурс та інваріант (invariant), зміст і при-
значення розрахунку ЛР2, звіт і потік подій, які формує платформа.

1.10 Спільна тема двох курсів
Для спільної теми C01–C30 можна виконати один проєкт на два курси. Спільні компоненти й
предметну логіку не потрібно реалізовувати двічі. Проєкт має забезпечувати ядро обох курсів
і вибрані розширення; у README окремо зіставте результати з пунктами Web і DPC. Захист
один, після готовності всього проєкту. Викладач застосовує перевірки check для обох курсів і
обговорює з командою спільну реалізацію.
Сервіси можуть використовувати спільні PostgreSQL і Kafka; частина Web надає інтерфейс
користувача, а частина DPC — відповідні обчислення та оброблення даних. Спосіб їх взаємодії
визначає картка спільної теми. Для кожного курсу команда окремо визначає вибрані розши-
рення. Кожен курс можна виконати й окремо; потрібні відповіді та події відсутньої частини
тоді відтворюють генераторами й імітаторами.
Спільна база не означає повторного виконання операції. Кожну зміну предметного стану
виконує одна частина проєкту; інша передає їй команду або читає вже зафіксований резуль-
тат, а повторна передача зберігає ідентифікатор операції. Якщо обидві частини змінюють той
самий ресурс (наприклад, сайт через Web і кол-центр через чергу DPC), вони застосовують
однакове предметне правило. Перевірка цього правила та зміна ресурсу виконуються атомар-
но в базі даних; кожна частина обробляє лише свої запити. Розділ 6 картки визначає спіль-
ні ідентифікатори та відповідальність компонентів за зміни стану. Масові дії користувачів і
зовнішніх пристроїв можна відтворювати генератором запитів. Стан змінюють сервіси, які
обробляють ці запити. Якщо проєкт виконується лише в одному курсі, потрібні дані, події та
відповіді відсутньої частини відтворюють генератори й імітатори відповідно до картки.

2.1 ЛР1. Сервіс із чергою та модель виконання
Матеріал лекції 3; О1.4 — також лекції 5. Сервіс приймає запити в обмежену чергу, обро-

Основні пункти
О1.1 Ядро. Приймання запитів. Реалізуйте маршрут із картки: прийнятий запит отримує
202 до завершення оброблення. Використайте стани queued → processing → done |
rejected | failed. rejected означає відхилення за предметним правилом, failed —
помилку оброблення. Під час роботи сервісу кожен прийнятий запит переходить у кін-

О1.2 Ядро. Обмежена черга й перевантаження. Використайте обмежену чергу (bounded
queue) місткості QUEUE_CAPACITY. Назвіть примітив синхронізації та поясніть очікува-
ння обробника, коли черга порожня. Якщо місця немає, одразу повертайте 429 з Retry-

значеному середовищі. Наведіть місткість черги, кількість обробників, кількість одно-
часних клієнтів і тривалість досліду.
О1.3 Ядро. Пул обробників. Запустіть рівно WORKERS обробників. Кожен запит проходить
повільний виклик із картки, після чого виконується предметна зміна. Очікування по-
вільного виклику не повинно блокувати приймання інших запитів.
О1.4 Ядро. Захист спільного ресурсу. На окремих тестових даних покажіть порушення ін-
варіанта без синхронізації. У робочому режимі критична секція охоплює перевірку й
зміну ресурсу. Повільний виклик виконується поза критичною секцією. Повторіть той
самий сценарій і перевірте інваріант.
О1.5 Час виконання й метрики. Фіксуйте монотонним годинником надходження запиту,
початок і завершення оброблення та першу видачу кінцевого результату через GET. До
читання результату позначки видачі немає. Обчисліть очікування в черзі, оброблення
й очікування видачі; перевірте порядок позначок. Додайте до/metrics довжину черги,
кількість запитів в обробленні та відхилень. Для p50, p95 і p99 явно назвіть вимірюва-

області.

Д1.2 Перевірка закону Літтла на вимірах.
Д1.3 Власна черга на м’ютексі й умовній змінній.

Д3.1 Порівняння акторів і задач Ray на тому самому сценарії.

кількість рядків, фактичний розмір, початкове значення генератора та виміряну час-
тку гарячого ключа. Та сама команда за однакових версій залежностей відтворює набір.
Обсяг 1–2 ГБ — орієнтир розширеного досліду, а не умова правильності звіту.
О4.2 Ядро. Пакетний звіт через API. Підготуйте невеликий відтворюваний набір своєї
теми генератором або явно заданими тестовими даними. Реалізуйте задачу Spark
зі з’єднанням довідника та групуванням засобами DataFrame або SQL. POST /v1/
reports/main/refresh запускає її; GET /v1/reports/main повертає стан і результат.
Великий набір з О4.1 не є передумовою перевірки правильності цього пункту.
О4.3 Ядро. Незалежний еталон. Обчисліть еталон без Spark на тому самому наборі й на-
дайте його через GET /v1/reports/main/reference . Порівнюйте групи за ключами, а
не порядком рядків. Лічильники й суми точних величин збігаються точно; середні та
частки — у межах зазначеного допуску. Середнє обчислюйте через загальну суму й кіль-
кість, а не як середнє частинних середніх.
О4.4 План виконання та перекіс даних. Збережіть фізичний план, поясніть оператори пе-
ретасування (shuffle) Exchange та часткову агрегацію. За метриками визначте, чи спри-
чиняє гарячий ключ перекіс даних (data skew) на досліджуваній стадії. Порівняйте по-
чатковий варіант з одним способом зменшення перекосу: соленням ключа (salting) або
адаптивним виконанням запитів (Adaptive Query Execution, AQE) з поділом перекоше-
них частин з’єднання. Цей механізм AQE стосується з’єднання, а не довільного агрегу-
вання. Перед запуском сформулюйте очікування; після запуску порівняйте тривалість
задач і звіт з еталоном. Дані та інші параметри залишаються однаковими. Якщо по-
мітного перекосу немає, поясніть це за планом і метриками; відсутність прискорення
також є результатом. Використайте відповідний набір з О4.1 або готові дані.
О4.5 Втрата виконавця Spark. Під час обчислення завершіть один виконавець Spark. Пере-
вірте завершення задачі та відповідність результату еталону.
Додаткові пункти
Д4.1 Реалізація й порівняння обох способів усунення перекосу.
Д4.2 Порівняння з’єднання з розсиланням довідника (broadcast join) і з’єднання з перетасу-
ванням (shuffle join).
Д4.3 Атомарна публікація звіту. Створюється новий каталог і замінюється вказівник на
нього.
Д4.4 Вплив одного фактора. Окремо дослідіть кількість частин даних (partitions) або час-
тку гарячого ключа. Змінюйте один фактор, сформулюйте передбачення та зіставте йо-
го з вимірюваннями.

2.5 ЛР5. Потокова обробка, запізнення й відновлення
Матеріал лекції 12. Потік подій агрегується в Spark Structured Streaming за часом події у ві-
кнах або на контрольних межах відповідно до предметного показника; відновлення з кон-
трольної точки не створює повторного результату. Окремі пункти досліджують дублікати вхі-
дних подій і вплив допустимого запізнення.
Основні пункти
О5.1 Сценарії джерела та дублікати подій. Опишіть поля події своєї картки, зокрема ста-
більний ідентифікатор і час події. Готовим або власним генератором створіть сценарії
з повторенням подій та передайте їх у тему Kafka (topic) з картки. Реалізуйте усунен-
ня дублів у межах визначеного часового горизонту й покажіть, що вони не змінюють
результат.
О5.2 Ядро. Агрегування за часом події. Використайте базовий набір подій своєї теми без
дублів. Налаштуйте тип і тривалість вікна, для ковзного вікна — також крок, та допусти-
ме запізнення (watermark delay). Якщо картка задає стан на контрольну межу часу, об-
числюйте його з початкового стану й переходів до цієї межі; початок нового інтервалу
не обнуляє стан. Період між контрольними межами визначає картка. Це спосіб отри-
мати предметний показник у цьому пункті, а не додаткове завдання. GET /v1/panel
повертає лише фіналізовані результати вікон або контрольних меж — ті, які більше не
оновлюються за прийнятим правилом допустимого запізнення. У README назвіть по-
дію, яка просуває межу часу подій (watermark) достатньо для фіналізації останнього
перевірюваного результату скінченного набору. Генерація й надсилання базового на-
бору потрібні для цього пункту; розширені сценарії О5.1 — ні.
О5.3 Вплив допустимого запізнення. На тій самій керованій послідовності порівняйте два
значення допустимого запізнення. Покажіть враховані й відкинуті події, частку відки-
нутих подій і затримку отримання результату. Перед запуском сформулюйте очікува-
ння. Поясніть, чому подія поблизу межі ще може бути врахована. Умови подання й
порядок подій у двох дослідах мають бути однаковими. Для контролю порядку викори-
стайте одну партицію Kafka або опишіть інший спосіб.
О5.4 Ядро. Відновлення без повторного результату. Зберігайте контрольну точку
(checkpoint) потокової задачі. Примусово завершіть задачу й відновіть її з тієї самої
контрольної точки. Записуйте результат ідемпотентно: вставленням або оновленням
запису за предметним ключем і вікном або контрольною межею (upsert) чи транзакцій-
ним обліком ідентифікатора мікропакета. Повторне виконання не створює другого
запису того самого результату й не застосовує перехід стану повторно. Порівняйте
результат із запуском без відмови. Поясніть, як приймач обробляє повторну доставку
мікропакета через foreachBatch.
О5.5 Ядро. Порівняння з пакетним розрахунком. Реалізуйте GET /v1/panel/batch для то-
го самого набору подій і тих самих правил агрегування. Використайте сценарій, у яко-
му всі перевірювані події надходять у межах допустимого запізнення. Порівняйте пре-
дметні ключі, вікна або контрольні межі та значення результатів. Якщо виконано О5.1,
застосуйте однакове правило усунення дублів в обох розрахунках.
Додаткові пункти

Д5.2 Власний стан із тайм-аутом для сеансу.

2.6 ЛР6. Координація виконавців
Матеріал лекцій 13–14. Координатори узгоджують власника ролі через etcd. Ресурс приймає
зміни лише від власника з чинним зареєстрованим поколінням, навіть якщо попередній про-
цес продовжує працювати.
Основні пункти
О6.1 Ядро. Отримання ролі через оренду. Запустіть два координатори. Організуйте отри-
мання ролі через оренду etcd (lease) зі строком життя (time to live, TTL) не більше 5 с
та її продовженням. GET /v1/coordinator повертає власника й покоління. Виміряйте
перехід ролі після зупинки власника; зазначте, від якої до якої події виміряно час.
О6.2 Ядро. Захист ресурсу перевіркою покоління. Новий власник реєструє своє покоління
на ресурсі. Захист перевіркою покоління (fencing) спирається на таблицю зареєстрова-
них поколінь та історію операцій. Ресурс перевіряє покоління в одній транзакції з пре-
дметною зміною та записом історії. Операцію приймають лише для зареєстрованого
поточного покоління; застаріле або незареєстроване покоління відхиляють. Перевірка
лише в координаторі недостатня.
О6.3 Старий власник після паузи та перевірка історії. Призупиніть координатор A дов-
ше за строк оренди. Дочекайтеся, поки B отримає роль і зареєструє нове покоління на
ресурсі. Відновіть A та перевірте відхилення його записів зі старим поколінням. GET
/v1/history повертає історію; одна команда перевіряє інваріант і відсутність прийня-
тих записів старого покоління після реєстрації нового. На окремих тестових даних по-
вторіть сценарій без захисту й покажіть порушення інваріанта.
Додаткові пункти
Д6.1 Перевірка лінеаризовності історії одного регістра.
Д6.2 Годинники Лемпорта в журналах координаторів і ресурсу.
Д6.3 Запис архітектурного рішення у відповідь на зміну обмеження.
Д6.4 Розгортання платформи на кількох вузлах (Docker Swarm або Kubernetes) і повторення
дослідів ЛР3 і ЛР6 з відмовою цілого вузла.
Типові помилки
• Перевіряти покоління лише в координаторі, а не на ресурсі.
• Брати як покоління поточний час або випадкове число замість ревізії etcd.
• Вважати оренду достатнім захистом без перевірки покоління на ресурсі.
• Ставити TTL менший за звичайну паузу процесу без продовження оренди.

3 Теми
Картки DPC описують ресурс і предметний ефект, пропоновані дані й маршрути, обчислю-
вальну модель, пакетний звіт, потік подій і координовану роль.
Назви таблиць, поля й предметні URL можна адаптувати, зберігаючи зміст операцій, інва-
ріанти та узгоджений контракт API. Службові маршрути й протокол керованих відмов визна-
чено у вступі та завданнях ЛР . Приклади відмов у картці пояснюють місце зупинки та очіку-
ваний результат; їх виконують у межах вибраних пунктів. Блок «Межі проєкту» відокремлює
навчальну модель від можливостей повноцінного продукту.
Як читати дані потокового сценарію. event_id позначає унікальну логічну подію, а не
предметний об’єкт. Повторна доставка зберігає цей ідентифікатор і вміст. Кілька справжніх
подій одного об’єкта мають різні ідентифікатори. Поле event_time містить час події; затрим-
ка доставки його не змінює.
Профілі в картках задають приклади ключів, вікон і агрегатів. Межі фіксованих і ковзних
вікон відраховуються від Unix epoch у UTC; початок включено, кінець — ні. Контрольний на-
бір для ядра містить унікальні події; сценарії з дублями належать до відповідного вибраного
пункту. Порівняння з пакетним еталоном використовує ті самі правила відбору подій.
Підрахунок подій за інтервал і стан об’єктів на його кінець — різні показники. Для стану по-
трібні початковий знімок або попередня історія; межа інтервалу не обнуляє стан. Наприклад,
20 пасажирів, які сіли раніше, і 5 нових посадок дають 25 пасажирів на борту. Якщо в роботі
було 7 заявок, прийнято ще 3 й завершено 2, у роботі залишається 8. За наявності запізнень
це стан на відповідну межу часу подій, а не миттєвий стан за настінним годинником.
Для невеликого навчального набору стан можна отримати з підготовленого знімка та впо-
рядкованих переходів і зберегти результат за ключем предметного об’єкта й контрольної ме-
жі. Фіналізація, відновлення й пакетний еталон використовують однакові початкові дані, пра-
вила порядку та допустимого запізнення. За однакового часу переходів джерело задає їхню
послідовність або версію; самого часу надходження для вибору останнього стану недостатньо.
Приклади запізнень не задають автоматично допустимого запізнення: це параметр кон-
кретного досліду. Аналітичний сигнал не змінює предметний стан, якщо така дія окремо не
визначена моделлю.
Наприклад, для хвилинного підрахунку дві події одного ключа з часом 12:00:10 і 12:00:40
дають результат 2 у вікні [12:00:00; 12:01:00). Для фіналізації джерело має просунути час по-
дій достатньо далеко з урахуванням налаштованого допустимого запізнення. Події наступно-
го інтервалу також є частиною вхідних даних, а їхні вікна не входять до цього контрольного
порівняння. Порожній мікропакет може бути потрібний для застосування вже оновленої межі
часу; саме очікування за годинником не замінює просування часу подій.

4. Обчислювальна модель. Функція λ(t) = A t e−t/τ на проміжку [0; T ]; первісна −Aτ (t +

ність, експоненційний час перевірки й одні ворота (формула M/M/1).
5. Предметні сценарії. Повторення задачі. Предметний результат — погашення квитка
(повторне сканування з новим scan_id повертає те саме рішення) рівно один раз за ключем
ticket_id після відмови виконавця.
Пакетний звіт. Проходи й медіана часу приходу за подіями й воротами; гарячий ключ —
концерт хедлайнера (60 % рядків).
Потік подій. Джерело — топік scans. Фіксоване вікно 1 хвилина; ключ — gate; кількість
подій успішного проходу ( accepted=true ). Приклад запізнення: ворота без зв’язку виванта-
жують буфер до 10 хвилин пізніше; повторна відправка дає дублі.
Координація. Роль — розподільник повернених місць; захищений запис — призначення
місця покупцю з черги очікування. Ресурс відхиляє цей запис, якщо покоління застаріле або
ще не зареєстроване. Якщо перевірку покоління вимкнути, старий розподільник після паузи
віддає вже продане місце.
Приклади відмов і очікувана поведінка.
• Процес отримує сигнал завершення з повною чергою запитів /v1/scans. У сі прийняті
запити обробляються до завершення.
• Виконавець завершується після запису ефекту «погашення квитка (повторне сканування
з новим scan_id повертає те саме рішення)», але до підтвердження задачі Ray. Повторне
виконання задачі не змінює предметного стану вдруге.
• Виконавець Spark завершується під час оновлення звіту. Після відновлення обчислень
звіт збігається з еталоном.
• Потокова задача завершується під час обробки потоку scans. Після відновлення з тієї
самої контрольної точки результат збігається з результатом без відмови.
• Власника ролі «розподільник повернених місць» призупинено на час, довший за TTL.
Новий власник реєструє покоління, після чого ресурс відхиляє запис старого власника.
6. Спільний проєкт з Web. Спільні ідентифікатори — performance_id, ticket_id. Продаж
квитків і облік місць за категоріями виконує тільки Web. DPC на вході перевіряє квиток через
GET /v1/tickets/{code} Web і веде лише заповненість секторів фан-зони; погашення квитка
за ticket_id записує тільки DPC. Для черги очікування Web спочатку резервує доступне місце
й вилучає його з вільного продажу; ідентифікатор резервування передається DPC. Розподіль-
ник DPC призначає лише таке зарезервоване місце й записує призначення у свою таблицю з
перевіркою покоління, а Web оформлює за ним квиток один раз (ключ — ідентифікатор при-
значення). Резерв не повертається у вільний продаж до завершення або узгодженого скасува-
ння призначення. За окремого виконання DPC чинні квитки й зарезервовані місця задаються
початковими даними; продаж квитків не реалізується.
