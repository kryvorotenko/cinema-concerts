1 Вступ
1.1 Як проходить робота
1. Команда. Проєкт виконує команда з 2–4 осіб. Кожне завдання виконують один раз на
проєкт; роботу команда розподіляє сама. README вказує внесок кожного учасника.
2. Вибір теми. До ЛР1 команда обирає спільну тему C01–C30 або тему курсу W01–W10. У
межах групи теми не повторюються. Власну предметну область (domain) можна запро-
понувати, якщо для неї можна заповнити всі поля картки; її погоджує викладач.
3. Завдання й картка. Пункти лабораторних робіт однакові для всіх тем ( розд. 2). Картка
(розд. 3) описує предметну область і містить пропоновані дані, маршрути, сценарії та ва-
ріанти розвитку системи. Реалізуйте можливості, потрібні для ядра й вибраних пунктів
лабораторних робіт. Структуру даних і предметні маршрути можна адаптувати, зберіга-
ючи інваріанти та узгоджений контракт API.
4. Шість робіт. Кожна ЛР розвиває той самий проєкт. Позначка Ядро виділяє обов’язкові
пункти. Решта основних пунктів — бажане поглиблення, а додаткові пункти пропону-
ють подальші досліди й можливості. Команда обирає їх відповідно до бажаної глибини
роботи. Вимоги вже виконаних пунктів залишаються чинними. Якщо розширення вико-
ристовує інший пункт, цю залежність зазначено в завданні.
5. Захист. Готовий проєкт захищається цілком після завершення роботи над усіма шістьма
ЛР: ядром і вибраними розширеннями. Команда запускає систему й демонструє резуль-
тати за README. Викладач перевіряє проєкт своїм засобом check, переглядає код, ре-
зультати дослідів і ставить запитання всім учасникам. Для спільного проєкту двох курсів
проводиться один захист після готовності обох частин.

1.4 Технології
У завданнях використано PostgreSQL, nginx, Kafka й Docker Compose. У лекціях на їхньому при-
кладі пояснюються принципи побудови та взаємодії компонентів системи. Можна викори-
стовувати інші технології, що забезпечують потрібні механізми, наприклад HAProxy замість
nginx, RabbitMQ замість Kafka або Kubernetes замість Docker Compose. Обрані технології за-
значте в README та поясніть, як вони забезпечують виконання вимог.
У додаткових матеріалах, які надаються разом із курсом, є каркаси програм, конфігура-
ції середовища, генератори даних та засоби проведення дослідів. Інструкції з використання
наведено у відповідних README. Надані компоненти можна адаптувати до своєї теми або роз-
робити власні. Під час захисту команда пояснює їхню роботу й демонструє виконання вимог.
Використані готові рішення та власний внесок зазначають у README.

1.6 Що має бути в результаті
Репозиторій містить сервер із двома екземплярами за балансувальником, клієнт, міграції,
контракт openapi.yaml, публікатор і обробник подій, два шлюзи WebSocket. Реалізовані ме-
ханізми ядра — предметний інваріант, ідемпотентність, доступ, таблиця вихідних подій, до-
ставка сповіщень, зміна схеми й коректне завершення. Решта можливостей визначається ви-
браними пунктами.
1.7 Керовані відмови
Керований дослід відтворює відмову в проміжку між діями, які не можна виконати атомар-
но. Для відмов у коді використовуйте протокол комплекту: FAULTS=on дозволяє режим, файл
/faults/<name> вмикає відмову в названому місці. Процес забирає прапорець, записує fault.
hit і негайно аварійно завершується без штатного завершення роботи. Один прапорець має
спричинити одну відмову; це має враховувати наявність кількох процесів. Зупинку контейне-
ра й паузу координатора відтворюють окремими діями.
README називає місце відмови, команду її ввімкнення, запис журналу та спосіб віднови-
ти початковий стан. Таблиця нижче описує можливі досліди; виконують ті, що належать до
вибраних пунктів.

1.8 Репозиторій і README
Репозиторій містить код сервера й клієнта, міграції, openapi.yaml, файли запуску контейне-
рів. README описує проєкт так, щоб людина, яка бачить його вперше, зрозуміла, з яких те-
хнологій і компонентів він складається, що з чим взаємодіє і що відбувається під час роботи.
Схеми вітаються. README містить такі розділи:
1. Курс і тема. Назва курсу, ідентифікатор і назва теми, склад команди.
2. Проєкт. Що робить система, ролі, головна операція, інваріанти (invariant).
3. Архітектура. Компоненти й технології, як вони взаємодіють (на схемі — клієнт, балансу-
вальник, екземпляри сервера, база, брокер, обробник, симулятор, шлюз), шлях головної
операції й сповіщення.

2.2 ЛР2. Конкуренція та повторення запитів
Матеріал лекцій 4–5. Головна операція зберігає інваріант за одночасних запитів і не повто-

Основні пункти
О2.1 Ядро. Інваріант за одночасних запитів. Забезпечте інваріант атомарним умовним
записом, блокуванням рядка або серіалізовною транзакцією з обмеженим повтором.
Обґрунтуйте вибір у README. Виконайте дослід із картки через обидва екземпляри й
перевірте підсумковий стан ресурсу. Засіб створення одночасних запитів може бути го-
товим або власним; реалізація повторів у клієнті з О2.4 для цього досліду не потрібна.
О2.2 Ядро. Механізм ідемпотентності. Реалізуйте механізм ідемпотентності відповідно
до наведених вимог. Якщо використано готовий компонент, поясніть збереження клю-
ча, перевірку параметрів і атомарність фіксації результату. Для головної операції за-
головок Idempotency-Key обов’язковий (немає — 400). Зберігаються користувач, опе-
рація, ключ, відбиток тіла, стан, відповідь і строк — в одній транзакції з предметною
зміною. Повтор із тим самим тілом — та сама відповідь; з іншим — 422; ключ ще обро-

О2.3 Повтор після втраченої відповіді. Додайте керовану відмову after_commit_before_
response: після фіксації транзакції процес завершується до надсилання відповіді. По-
вторіть запит із тим самим ключем через інший екземпляр. Перевірте, що повертає-
ться збережений результат, а предметна зміна виконана один раз.

вим розсіюванням (jitter); пауза не менша за Retry-After. Обмежте кількість спроб і
загальний час очікування. Якщо результат установити не вдалося, показуйте «резуль-

О3.1 Ядро. Вхід. Користувачі з хешем пароля й роллю ( user, staff). Можна обрати сесію в

та Origin. Для токена поясніть місце його зберігання в клієнті. Покажіть дозволений і
заборонений сценарії.
О3.4 Сценарії входу й доступу в клієнті. Додайте вхід і вихід. Покажіть спробу отримати
чужий об’єкт і виконати функцію персоналу без відповідної ролі. Якщо виконано О3.3,
продемонструйте також запит зі стороннім Origin.

2.4 ЛР4. Довгі операції, події й зовнішня система
Матеріал лекцій 7–8. Операція, що звертається до зовнішньої системи, виконується асин-
хронно. У спішна операція не створює повторного ефекту під час повторного виконання; від-
хилена завершується з поясненням причини. Матеріал лекції 9 допомагає організувати пере-
вірки.
Основні пункти
О4.1 Ядро. Асинхронна операція. Підготуйте таблиці операцій, вихідних подій, обробле-
них повідомлень і сповіщень. Маршрут із картки створює операцію та повертає 202,
Location: /v1/operations/{op} і Retry-After. Повтор із тим самим ключем повертає
ту саму операцію. Маршрут її стану доступний лише власнику й повертає стан (pending,
running, succeeded, failed), версію та результат. Карантин потрібний лише для Д4.4.
О4.2 Ядро. Таблиця вихідних подій і публікатор. Реалізуйте шаблон транзакційної табли-
ці вихідних подій (Transactional Outbox). Записуйте подію в тій самій транзакції, що
змінює предметний стан. Окремий публікатор читає порції з FOR UPDATE SKIP LOCKED
і позначає їх опублікованими після підтвердження брокера. Подія містить стабільний
id, тип, ідентифікатор і версію сутності та час. Ключ повідомлення — ідентифікатор
сутності. Повторна публікація зберігає id; запит не надсилає подію в брокер безпосе-
редньо.
О4.3 Ядро. Обробник події. Викликайте симулятор із ключем, що дорівнює ідентифікатору
операції, та з обмеженим часом очікування. Зовнішню дію виконує симулятор; локаль-
на транзакція її не охоплює. Стан операції, предметні зміни, позначку «обробник —
подія» та сповіщення користувачу фіксуйте однією транзакцією. Підтверджуйте пові-
домлення брокеру після фіксації. Розрізняйте успішний результат, відхилення за пре-
дметним правилом і тимчасову недоступність зовнішньої системи. Читання стрічки
сповіщень належить до О5.3.
О4.4 Відновлення після керованих відмов. Перевірте publisher_before_send і after_
external_before_commit. Після перезапуску подія має бути опублікована й оброблена.
Повторний виклик симулятора з тим самим ключем повертає збережений результат.
Для успішної операції перевірте один зовнішній ефект за GET /effects та одне спо-
віщення; для відхиленої — відсутність успішного предметного ефекту та узгоджений
кінцевий стан.
О4.5 Клієнт асинхронної операції. Додайте запуск операції та опитування її стану з до-
триманням Retry-After. Покажіть кінцевий результат або причину невдачі. Стрічка
сповіщень належить до ЛР5.
Додаткові пункти
Д4.1 Формат подій CloudEvents 1.0.
Д4.2 Опис каналів і повідомлень в AsyncAPI 3.0.
Д4.3 Наскрізна траса однієї операції через HTTP , брокер і обробник.
Д4.4 Проблемні повідомлення. Не більше N спроб із паузою, далі — карантин ( domain-
events.dlq або таблиця) з причиною; повторне оброблення з карантину зберігає іден-
тифікатор події.

2.5 ЛР5. Сповіщення через WebSocket
Матеріал лекцій 6 і 8. Основний сценарій — авторизоване підключення й доставка спові-
щень користувачу через два шлюзи. Інші пункти додають стрічку, відновлення після розриву,
роботу з повільним клієнтом і дослідження балансування. Гарантія дочитування пропущено-
го стосується реалізації з О5.3.
Основні пункти
О5.1 Ядро. Авторизоване підключення. Реалізуйте POST /v1/ws-tickets : одноразовий
квиток зі строком дії 30 с. Перед прийняттям з’єднання /v1/ws?ticket= перевіряйте
квиток і Origin. Користувач отримує лише власні сповіщення. Під час виходу закри-
вайте з’єднання відповідної сесії кодом 1008; опишіть зв’язок сесії зі з’єднаннями.
Для JWT видалення токена в клієнті саме по собі не повідомляє шлюзи про вихід:
потрібний явний сигнал від маршруту виходу.
О5.2 Ядро. Доставка через два шлюзи. Кожен шлюз отримує з notifications всі сповіще-
ння через власну групу споживачів або власну чергу та надсилає їх своїм з’єднанням
потрібного користувача. Забезпечте передавання сповіщень, записаних у ЛР4, до цьо-
го каналу. Наприклад, обробник записує вихідну подію сповіщення в тій самій транза-
кції, а публікатор передає її до notifications. Покажіть доставку двом клієнтам одно-
го користувача, підключеним до різних шлюзів. Повторно отримане сповіщення не за-
стосовується клієнтом удруге. Для демонстрації достатньо мінімального клієнта або
сценарію; стрічка й відновлення з О5.3 для цього пункту не потрібні.
О5.3 Стрічка сповіщень і відновлення. Реалізуйте GET /v1/me/notifications?after= та
GET /v1/me/notifications/head . Стрічка містить сповіщення користувача з позиція-
ми, що зростають; повторна доставка не створює дубля. Клієнт установлює підписку,
тимчасово накопичує нові сповіщення, читає межу й історію до неї, після чого засто-
совує накопичені сповіщення без повторів. Після розриву він підключається знову й
дочитує історію від останньої застосованої позиції. Перевірте випадок, коли сповіще-
ння створене між установленням підписки та читанням межі. Порядок позицій і чита-
ння історії не повинні допускати пропуску пізніше зафіксованого запису. Оброблення
застарілого курсора належить до Д5.8.
О5.4 Клієнт сповіщень. Додайте до клієнта підключення з квитком і показ сповіщень нажи-
во. Якщо виконано О5.3, додайте показ історії, повторне підключення й дочитування
пропущеного.
Додаткові пункти
Д5.1 Адресна маршрутизація з реєстром «користувач — шлюз» і орендою; дослід видалення
маршруту із затримкою.
Д5.2 Відображення присутності користувачів у мережі.
Д5.3 Server-Sent Events як другий канал.
Д5.4 Розподіл 100 з’єднань і використання пам’яті шлюзом за такого навантаження.
Д5.5 Контроль з’єднання. Налаштуйте контрольні сигнали (heartbeat) та узгодьте їхній ін-
тервал із proxy_read_timeout: інтервал коротший за час очікування проксі. Перевірте
виявлення розірваного з’єднання. Наведіть налаштування Upgrade, Connection та часу

2.6 ЛР6. Зміна системи та поступове оновлення
Матеріал лекції 10. Виконайте заплановану зміну з картки, визначте умови повернення по-

Основні пункти
О6.1 Ядро. Запланована зміна та повернення попередньої версії. Виконайте зміну з кар-
тки: розширте схему, забезпечте перехідний режим і за потреби заповніть нові поля
порціями. Увімкніть нову поведінку прапорцем функції (feature flag) після перевірки
даних. Застарілі елементи видаляйте лише тоді, коли їх більше не використовують. У
README зазначте, до якого кроку можна повернути попередню версію та які дії потрі-
бні для цього. Перевірте повернення до цієї межі й поясніть стан даних після неї. Якщо
зміна не має незворотного кроку, поясніть це.
О6.2 Сумісність. Автоматичний тест надсилає збережені запити клієнта попередньої версії
до нової версії сервера й перевіряє відповіді; подія попередньої схеми обробляється
новим обробником; таблиця сумісності версій у README.
О6.3 Ядро. Готовність і коректне завершення. Після сигналу SIGTERM переведіть процес у
режим коректного завершення (graceful shutdown): /ready повертає 503, розпочаті за-
пити завершуються в межах установленого часу. Обробник підтверджує лише зафіксо-
вані результати. Шлюз поступово закриває з’єднання кодом 1012. Покажіть, як процес
припиняє приймати нову роботу; сам прапорець готовності не замінює цього механі-
зму.
О6.4 Поступове оновлення під навантаженням. Перевірте сумісність за О6.2, а потім оно-
віть app-a і app-b по черзі. Укажіть кількість запитів, тривалість досліду та правило
підрахунку помилок. Частка технічних помилок не перевищує 0,5 %; очікувані відхиле-
ння за предметними правилами обліковуйте окремо. Якщо виконано О5.3, перевірте
відновлення сповіщень під час оновлення відповідних компонентів.
Додаткові пункти

Д6.2 Канаркове оновлення з частиною трафіку на новій версії.
Д6.3 Прапорці функцій як окремий сервіс конфігурації.
