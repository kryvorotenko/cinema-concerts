# DPC: справочник лабораторных

Источник: DPC-методичка, стр. 7–17; C01 стр. 20–22. При упоминании ниже
источника `scans` в текущем проекте используйте согласованное имя топика
`ticket-telemetry`; контракт и поля — `docs/contracts/README.md`.
**Ядро обязательно; остальные О и Д выбираются отдельно.** Точные тексты:

## ЛР1. Очередь и модель выполнения (стр. 7–8)

Ядро: **О1.1, О1.2, О1.3, О1.4**.

- О1.1: C01 POST `/v1/scans` → **202 до окончания обработки**; queued→processing→done/rejected/failed. rejected = предметный отказ, failed = техническая ошибка. Каждый принятый запрос при работающем сервисе достигает конечного состояния. GET состояния запроса/ресурса, БД/миграции. Сохранение очереди после аварии пока не требуется.
- О1.2: bounded queue **QUEUE_CAPACITY**, назвать примитив и объяснить ожидание пустой очереди. Полная → немедленно **429 + Retry-After**, запрос не принимается. В воспроизводимом опыте полной очереди **p95 `/health` <=100 мс**; указать среду, capacity, WORKERS, concurrent clients, duration.
- О1.3: ровно **WORKERS** обработчиков; проверка билета **100–500 мс**, ожидание не блокирует приём.
- О1.4: на изолированных данных показать нарушение без синхронизации; затем тот же опыт с защитой. Проверка + изменение sector внутри критической секции; медленный Web-вызов вне неё. Ресурс — заполненность сектора, не остаток категории Web.
- О1.5: monotonic timestamps arrival/start/finish/first final GET, до чтения нет issued timestamp; queue wait/processing/issue wait, порядок меток; `/metrics` queue length/in-flight/rejections; p50/p95/p99 с явными интервалом и выборкой. HTTP latency не полное время выполнения.

Д1.1 — сравнение двух execution models; Д1.2 — Little's law на измерениях;
Д1.3 — собственная mutex+condition queue; Д1.4 — SIGTERM, новые **503**,
**все принятые** обработаны, лог записан.

## ЛР2. Параллельный численный расчёт (стр. 9–10)

Ядро: **О2.1, О2.3, О2.4**.

- О2.1: POST `/v1/compute` с **a,b,n,workers,method,order**. Интегрирование C01 `A*t*exp(-t/tau)`; эталон первообразной в PROJECT. Разбиение без дыр/перекрытий, локальные суммы процессов → reduction. Возвращать value/reference/error/time/workers; проверить **1,2,4 процесса** при одинаковых параметрах и явном допуске. README: схема и последовательная часть. Эталон обязателен без О2.2.
- О2.2: обоснование ошибки метода и округления; n и 2n, где методическая ошибка заметна. Если метод точен для функции, порядок сходимости изучать на иной тестовой функции, сохраняя основной расчёт C01.
- О2.3: для **1,2,4** процессов **>=3 измерений**, median/spread, **Sp=T1/Tp, Ep=Sp/p**. **T1>=1 с**; физические ядра и состав времени (pool startup/data transfer). Профиль → одна гипотеза → изменить один параметр → перемерить **без профайлера**, сохраняя задачу/точность. Отрицательный результат допустим.
- О2.4: сравнить общую сумму без защиты, с lock и локальные суммы; реально показать lost updates; защищённые варианты в допуске эталона.

Д2.1 — иной метод карточки (Monte Carlo очереди ворот); Д2.2 — Richardson;
Д2.3 — static/dynamic scheduling; Д2.4 — последовательное/pairwise/compensated
суммирование и ошибки n/2n; Д2.5 — parallel histogram времени прихода по минутам,
local dictionaries + merge, равенство последовательному; Д2.6 — async GET/DELETE
`/v1/compute/{id}`, после cancel **<=1 с** до 0 активных частей, результата нет,
проверка сигнала между порциями.
Не использовать CPU-bound Python threads как доказательство многопроцессного ускорения;
float сравнивать с допуском, seed не зависит от номера процесса.

## ЛР3. Ray и восстановление (стр. 11)

Ядро: **О3.1, О3.3, О3.4**.

- О3.1: обработка принятых scans в Ray tasks, retry системной аварии. **Ресурс меняет приёмник результата, не Ray worker**. Ключ всех попыток эффекта C01 **ticket_id**.
- О3.2: **IN_FLIGHT_LIMIT**; сверх лимита ждать в очереди ЛР1, не бесконечно подавать Ray tasks; демонстрация slow execution.
- О3.3: таблица эффектов с unique ticket_id. Дедупликация + изменение sector + запись решения одной транзакцией. Повтор возвращает прежнее решение, в том числе новый scan_id того же билета.
- О3.4: fault **after_effect_before_ack** — Ray worker аварийно завершается после приёма эффекта, до окончания task; дождаться настоящего retry, проверить один эффект и инвариант.

Д3.1 — actors vs tasks; Д3.2 — расчёт ЛР2 через Ray на нескольких узлах;
Д3.3 — HTTP Idempotency-Key: то же тело→тот же ID, другое→**409**,
concurrent duplicates→один приём (не путать с **422 Web О2.2**);
Д3.4 — зависит от О3.2: два значения receiver delay при одинаковом остальном,
throughput/full completion p95/429 share и объяснение backpressure.
Принимать первый готовый task, а не ждать только в submission order.

## ЛР4. Spark batch (стр. 12–13)

Ядро: **О4.2, О4.3**. Большой набор и skew — не условие правильности ядра.

- О4.1: Parquet история + справочник C01, **>=100 000 строк**, правдоподобность и hot key; указать rows/actual bytes/seed/measured hot share. Версионированная команда воспроизводит данные. **1–2 ГБ лишь ориентир расширенного опыта**. C01: **60%** строк концерт хедлайнера.
- О4.2: малый воспроизводимый набор; Spark DataFrame/SQL join справочника + group-by. POST `/v1/reports/main/refresh`, GET `/v1/reports/main` state/result. C01: **число проходов и медиана времени прихода по событию и воротам**.
- О4.3: независимый от Spark reference на тех же данных через GET `/v1/reports/main/reference`; сравнивать ключи групп, не порядок строк. Целые counts/sums совпадают точно, средние/доли по допуску; среднее из sum/count, не среднее средних. Для медианы определить согласованные единицы/правило и независимый алгоритм.
- О4.4: physical plan, Exchange/shuffle и partial aggregation; метрики реального skew. Один способ salting либо AQE skew-join split; **AQE skew-join не лечит произвольную агрегацию автоматически**. Предсказание до опыта, после duration/result vs reference; те же данные/настройки. Нет skew/ускорения — тоже результат, объяснить.
- О4.5: завершить один executor во время расчёта, задача заканчивается и равна reference.

Д4.1 — оба способа skew; Д4.2 — broadcast vs shuffle join; Д4.3 — atomic publish
новым каталогом + заменой указателя; Д4.4 — один фактор partitions/hot share,
прогноз и измерения. Не считать весь отчёт Python-циклом после collect на driver.
При salting корректно дублировать справочник и восстанавливать агрегаты;
медиану нельзя получить средним/медианой частных медиан.

## ЛР5. Structured Streaming (стр. 14–15, 17)

Ядро: **О5.2, О5.4, О5.5**.

- О5.1: stable event_id + event_time, сценарии дубликатов Kafka; bounded event-time дедупликация, одинаковый результат. Реальные разные события одного объекта имеют разные ID.
- О5.2: базовый набор **без дублей**, event-time, явные тип/длина/шаг window и watermark delay. C01: **topic scans; fixed 1 minute; key gate; count accepted=true**. `/v1/panel` только **финализированные** результаты. Назвать событие, продвигающее watermark достаточно для последнего проверяемого окна конечного набора; проверить финализацию, а не просто отправку tick.
- О5.3: два watermark delay на **одной последовательности и порядке**; accounted/dropped IDs, dropped fraction/result latency; предварительный прогноз. Пограничная старая event может быть учтена; не объявлять все event_time<watermark гарантированно отброшенными. Для порядка одна Kafka partition либо обоснованный иной контроль.
- О5.4: принудительный kill stream → рестарт **с того же checkpoint**; idempotent sink `(key,window)` upsert либо transaction batch-ID ledger; повтор foreachBatch не создаёт дубль/двойную прибавку. Сравнить с запуском без отказа.
- О5.5: GET `/v1/panel/batch`, тот же input/правила, все проверяемые события в допустимом запаздывании. Сравнить keys/windows/values. При О5.1 одинаковая дедупликация обоих расчётов.

Д5.1 — второй window profile; Д5.2 — custom session state + timeout.
UTC ISO 8601 Z либо epoch milliseconds, точность **до мс**, формат закрепить
между source/stream/reference. Fixed/sliding окна выровнены по Unix epoch UTC,
**[start,end)**, boundary event идёт в следующее окно. Processing-time не event-time.
C01 пример задержки ворот **до 10 минут**, watermark выбирается отдельно.
Ждать по настенным часам недостаточно для watermark; после продвижения может
понадобиться пустой микропакет. Если используется служебный tick, его не считать
предметным проходом. Независимые опыты — изолированный input/checkpoint/output;
опыт восстановления — сохранённый checkpoint. Для других тем состояние на
контрольную границу не равно count событий, но C01 требует именно counts.

## ЛР6. Координация (стр. 16)

Ядро: **О6.1, О6.2**.

- О6.1: два координатора, etcd lease **TTL<=5 с**, renew; GET `/v1/coordinator` owner/generation; измерить failover после stop владельца, определить начальную/конечную события измерения.
- О6.2: новый владелец регистрирует generation **на ресурсе**. Generation registry + history, проверка **текущего зарегистрированного** поколения + предметный эффект + history одной транзакцией. Старое и незарегистрированное поколение отвергаются. Брать поколение из ревизии etcd, не wall-clock/random.
- О6.3: pause A **дольше TTL**, дождаться lease B и регистрации B на ресурсе, resume A; старые записи отвергаются. GET `/v1/history`, одна команда проверяет инвариант и отсутствие принятых old-generation после registration B. Повтор без fencing на изолированных данных показывает нарушение.

C01: роль **распределителя возвращённых мест**, не expiry cleaner.
Web заранее резервирует место, DPC назначает только этот reserve, Web выпускает
ticket один раз по assignment_id. Не переиспользовать reserve параллельно в свободной продаже.
Д6.1 — linearizability single register history; Д6.2 — Lamport clocks;
Д6.3 — ADR по изменению ограничения; Д6.4 — несколько машин и повтор ЛР3/6
с отказом целого узла (контейнеры одной машины не доказывают machine failover).
