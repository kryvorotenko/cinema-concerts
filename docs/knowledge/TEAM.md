которые не совпали с методичками, перечислены в DECISIONS.md и не становятся

| Участник | Договорённые лабораторные | Вертикальная зона с учётом карточки C01 |
|---|---|---|
| 1 — Web Core & Zero-Downtime | Web **1 → 2 → 3 → 6** | Модель/миграции Web, sync API, клиент, инвариант категорий, idempotency/auth/RBAC, переход к конкретным местам |
| 2 — Kafka / Async / Real-time | Web **4 → 5**, Kafka + external-sim в начале | Общий Kafka KRaft, платёжный симулятор, outbox/publisher/worker, два gateway, WS; catch-up если выбран О5.3 |

меняем согласованно; не реализуем один предметный эффект дважды.

## Первая синхронизация

План предлагает 2–3 часа совместной фиксации схемы и констант. До параллельной
реализации нужно записать:

1. Общие ID `performance_id`, `ticket_id`; `screenings.id = performance_id`,
   screening связан с event; отдельно определить
   scan_id/event_id/operation_id/reserve_id/assignment_id и их уникальность.
2. Версионированные миграции в общем каталоге: Web владеет продажами/hold/ticket,
   DPC — sector/scan/effect/assignment/history. Не объявлять исходный список
   users/events/screenings/seats/bookings окончательной схемой C01.
3. Авторизованный контракт проверки билета Web для DPC; тестовые fixtures или
   адаптер для независимой ранней разработки вместо второго сервиса продажи.
4. Контракты событий: `domain-events`, `notifications`, **`ticket-telemetry`**.
   Последний — согласованное пользователем имя для потока `scans` из карточки C01.
5. Резерв Web → assignment DPC → выпуск Web; правила отмены резерва и fencing.
6. Порты, имена Compose-сервисов, env vars, единая система миграций; совместное
   использование Postgres/Kafka реализовано в едином корневом Compose.
7. Выбранные дополнительные О/Д отдельно по каждому курсу; автоматического
   выбора всех пунктов по названию лабораторной нет.

## Реальные зависимости

- Web 4 опирается на hold/auth/idempotency и согласованную схему; Web 5 — на
  уведомления Web 4, shared auth/logout и Kafka.
- DPC 1 может разрабатываться на fixtures валидных билетов, но интеграционный
  путь обязан проверять Web; DPC 3 сохраняет инвариант DPC 1.
- Spark batch не зависит от готовности Ray. Поток требует Kafka и контракт ticket-telemetry,
  а reference должен работать независимо от Spark.
- DPC 6 требует от Web механизм резервирования для waitlist; это явная точка
  интеграции двух участников, а не полностью автономный cleaner.
- Web 6 требует сохранения старого контракта/версии до начала миграции.
