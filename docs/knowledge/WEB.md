## ЛР1. Контракт, модель и первая операция (стр. 7–8)

Ядро: **О1.1, О1.2, О1.3, О1.4, О1.7**.

- О1.1: сущности, диаграмма состояний, переходы, инварианты, численные учебные предположения в README.
- О1.2: версионные миграции; PK/FK/NOT NULL/CHECK/UNIQUE; деньги в минимальных целых единицах + валюта, точные величины integer/decimal, моменты timestamptz, даты date, имя временной зоны отдельно.
- О1.3: OpenAPI **3.1**, примеры запросов/ответов и examples тел изменений; Problem Details; проверка линтером.
- О1.4: проверка ресурса + изменение + основная сущность в **одной транзакции**, ответ после commit. Создание **201 + Location**, изменение 200/204; повреждённый JSON 400, неверные данные 422, нет ресурса 404, недостаток 409; JSON ID — строки. Владелец из аутентифицированного контекста, не тела.
- О1.5 (не ядро): доступный пользователю список от новых к старым, порядок `(time,id)`, limit **1–50**, непрозрачный next_cursor, испорченный курсор 400.
- О1.6 (не ядро): одна команда запуска nginx/app-a/app-b/postgres; `/health` каждого без БД; X-Request-ID на всех ответах; JSON-лог time/instance/route-template/status/duration без паролей/токенов.
- О1.7: клиент основного сценария, результат и Problem Details; терпимость к неизвестным полям; при О1.5 чтение всех страниц.

До ЛР3 используется X-User-Id заранее созданного пользователя.
Д1.1 — чистая функция временного правила с переданным now; Д1.2 — другая
языковая реализация клиента; Д1.3 — тест правила RFC 9110/9457; Д1.4 — проверенный
traceparent как trace_id; Д1.5 — деньги/округления/сроки/сутки/DST по карточке,
ISO 8601, отображение в зоне области, интервалы `[start,end)`.
Для C01 важно не заменить категорию конкретным креслом до запланированной ЛР6.

## ЛР2. Конкуренция и повторы (стр. 9–11)

Ядро: **О2.1, О2.2**.

- О2.1: атомарный условный UPDATE, блокировка строки либо serializable с ограниченным retry; обосновать. Проверить сценарий C01 **300 покупателей / 50 мест через оба экземпляра** и итоговый инвариант. Локальный mutex одного процесса недостаточен.
- О2.2: обязательный Idempotency-Key, без него **400**. В одной транзакции с эффектом хранить пользователя, операцию, ключ, отпечаток тела, состояние, ответ и срок. То же тело → тот же ответ; другое тело → **422**; ключ ещё обрабатывается → **409**. Чистить просроченные ключи порциями. Отпечаток не зависит от порядка полей JSON.
- О2.3: fault **after_commit_before_response**; повтор через другой экземпляр возвращает сохранённый результат, эффект один.
- О2.4: тот же ключ при всех попытках; exponential backoff + jitter, не раньше Retry-After; предел попыток и времени; при неопределённости показывать «результат неизвестен».

Д2.1 — общий для экземпляров rate limit изменений (429); Д2.2 — сравнить два
способа защиты на одинаковой нагрузке; Д2.3 — второй инвариант; Д2.4 — If-Match/ETag,
**412** устаревший, **428** отсутствует, проверка версии + запись одной инструкцией;
Д2.5 — повтор отмены не освобождает место повторно; Д2.6 — connection pool,
тайм-ауты соединения/SQL/запроса, **503 + Retry-After**, расчёт лимита соединений;
Д2.7 — **>=100 000 записей**, EXPLAIN (ANALYZE, BUFFERS) до/после индекса на тех же
данных, зависит от О1.5; не отключать seq scan ради красивого результата.

## ЛР3. Вход и доступ (стр. 12)

Ядро: **О3.1, О3.2**.

- О3.1: хеш пароля, user/staff; cookie-сессия, opaque token либо JWT. POST `/v1/auth/login`, POST `/v1/auth/logout`, GET `/v1/me`; оба экземпляра, expiry и logout; **X-User-Id больше не принимается**. Сессия/opaque token удаляются на сервере; JWT без Д3.1 остаётся действителен до exp после удаления на клиенте.
- О3.2: владелец/участник проверяется в SQL; чужой и отсутствующий объект одинаково **404**; попытки менять owner/state/version → **422**; staff-функция без роли → **403**. C01: staff закрывает продажу категории.
- О3.3: точный разрешённый origin, без `*`, OPTIONS; для cookie отклонять сторонние изменения **до эффекта** по Sec-Fetch-Site и Origin; для token объяснить хранение; разрешённый и запрещённый сценарии. CORS не равен CSRF-защите.
- О3.4: UI вход/выход, попытка чтения чужого и staff-функции без роли; если О3.3 — сторонний Origin.

Д3.1 — JWT revocation; Д3.2 — OIDC/Keycloak; Д3.3 — ограничение попыток входа.

## ЛР4. Долгие операции и внешняя система (стр. 13–14)

Ядро: **О4.1, О4.2, О4.3**.

- О4.1: таблицы operations/outbox/processed messages/notifications. C01 POST `/v1/holds/{id}/payments` → **202**, Location `/v1/operations/{op}`, Retry-After; повтор ключа → та же операция. Состояние только владельцу: pending/running/succeeded/failed, version/result. Карантин только Д4.4.
- О4.2: Transactional Outbox вместе с предметным изменением; отдельный publisher читает порциями **FOR UPDATE SKIP LOCKED**, published только после broker ack. Стабильные event id/type/entity id/version/time; message key = entity id. Повтор публикации сохраняет id. HTTP-handler не пишет прямо в Kafka.
- О4.3: worker вызывает симулятор с **ключом ID операции**, ограниченным timeout. Внешний эффект вне локальной транзакции. Локальные outcome/предметные изменения/дедупликация **(handler,event)**/уведомление — одна транзакция; broker ack после commit. Различать успех, бизнес-отказ и временную недоступность.
- О4.4: faults **publisher_before_send**, **after_external_before_commit**. После рестарта публикация/обработка завершается; один успешный внешний эффект через GET `/effects` и одно уведомление. Для отказа нет успешного предметного эффекта.
- О4.5: клиент запускает и опрашивает с Retry-After; показывает итог/причину.

Симулятор C01: POST `/charge`, **2–8 с, 20% отказ, 5% 503**. Сохраняет окончательный
успех/отказ по ключу; 503 не закрепляет. Конфигурируются seed/задержки/доли и
недоступность N секунд. Только Web выпускает билет; симулятор не пишет ticket в БД.
Проверить, как обеспечить одновременно ключ операции по О4.3 и одно списание
на hold по карточке при нескольких запросах оплаты одного hold; решение ещё не принято.

Д4.1 — CloudEvents 1.0; Д4.2 — AsyncAPI 3.0; Д4.3 — сквозная trace;
Д4.4 — <=N попыток с паузой, затем DLQ/табличный карантин с причиной,
повтор обработки сохраняет event_id.

## ЛР5. WebSocket (стр. 15–16)

Ядро: **О5.1, О5.2**.

- О5.1: POST `/v1/ws-tickets`, одноразовый билет **30 с**. До accept `/v1/ws?ticket=` проверить ticket и Origin. Только свои уведомления; logout закрывает соединения сессии кодом **1008**. JWT logout должен явно сигналить gateway, удаления токена недостаточно.
- О5.2: два gateway, **собственная consumer group/очередь каждого** получает все notifications. Доставка уведомлений ЛР4 в этот канал, например через outbox в транзакции worker. Два клиента одного пользователя на разных gateway оба получают сообщение; клиент не применяет дубль. Минимальный клиент/скрипт достаточен, история не обязательна этому пункту.
- О5.3: GET `/v1/me/notifications?after=` и `/head`; растущие позиции, без дублей. Алгоритм **подписка → буфер live → head → история до head → слить буфер без повторов**. При reconnect читать с последней применённой позиции. Проверить гонку между подпиской/head и поздним commit записи с меньшей позицией. Простой sequence ID сам по себе не гарантирует commit-order.
- О5.4: UI подключения и live; если О5.3 — история и reconnect/catch-up.

Д5.1 — registry user→gateway с lease и опыт задержанной очистки;
Д5.2 — presence; Д5.3 — SSE; Д5.4 — **100 соединений** и память;
Д5.5 — heartbeat короче proxy_read_timeout, Upgrade/Connection и опыт разрыва;
Д5.6 — bounded buffer, overflow close **1013**, если история есть — catch-up;
Д5.7 — least_conn, **20 соединений** до/после рестарта, существующие не мигрируют;
Д5.8 — retention истории, старый cursor **410**, перезагрузка текущего состояния,
зависит от О5.3. Не путать 410 расширения с обязательным ядром.

## ЛР6. Изменение и постепенное обновление (стр. 17)

Ядро: **О6.1, О6.3**.

- О6.1: **для C01 конкретные места по ряду/номеру вместо одного количества категории**. Старый клиент получает автоматическое назначение. Expand → совместимый переход → backfill порциями при необходимости → проверка данных → feature flag → contract лишь когда старое не используется. Зафиксировать границу rollback и команды, проверить возврат до неё; после объяснить судьбу данных. Не называть удаление новых данных откатом.
- О6.2: автоматические сохранённые запросы старого клиента к новому серверу, старая event schema к новому worker; матрица совместимости в README.
- О6.3: SIGTERM, `/ready` → **503**, прекратить приём новой работы отдельным механизмом, завершить начатую в установленный срок; worker ack только commit; gateway закрывает постепенно **1012**. Readiness=false не закрывает уже открытые соединения.
- О6.4: зависит от О6.2; app-a/app-b по очереди под нагрузкой, число запросов/длительность/правило ошибок; технические ошибки **<=0,5%**, бизнес-отказы отдельно; при О5.3 проверить уведомления при обновлении.

Д6.1 — ADR по изменению требования; Д6.2 — canary; Д6.3 — отдельный feature-flag
сервис; Д6.4 — несколько машин Swarm/Kubernetes и rolling средствами оркестратора.

## Служебные маршруты и транспорт

Все описывать в OpenAPI вместе с предметными. `/health` без БД с ЛР1;
`/ready` с проверкой доступности БД и 503 в drain с ЛР6. Клиент вне Compose,
обращается только к nginx. Два stateless app-инстанса, состояние в БД;
два WS gateway с ЛР5, отдельные publisher/worker с ЛР4, Kafka KRaft.
Названия domain-events, notifications; domain-events.dlq относится к Д4.4.
