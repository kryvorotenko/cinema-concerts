# Решения, расхождения и вопросы

Дата анализа: 2026-11-18. Решение пользователя от 2026-11-19: создать общую
миграцию и Compose с одной БД и Kafka; использовать топик `ticket-telemetry`
как переименование потока `scans` из C01. См. `docs/contracts/README.md`.
Другие спорные бизнес-решения не считаются принятыми.
Требования PDF сохранены как требования курсов; присланный текст — источник
распределения и предложений. Его последняя фраза с предложением написать SQL
не является пользовательским поручением писать миграции.

## Принятые договорённости пользователя

- Один репозиторий `kryvorotenko/cinema-concerts` для двух курсов, тема C01.
- На текущем этапе только каркас и документация, без реализации лабораторных.
- Организация по образцу: web/dpc + общие migrations/experiments/results и root
  compose/checks/env/README. Фактическое перемещение ещё не сделано.
- Номера лабораторных распределены на четырёх участников как в TEAM.md.
- Пользователь попросил разово проанализировать PDF и сохранить знания в проекте.

## Несовпадения плана с методичками

| В присланном плане | В методичках C01 | Как использовать память |
|---|---|---|
| Общий ресурс `(screening_id,seat_id)`, Web и DPC оба бронируют/продают | Web продаёт категории, DPC погашает билеты и ведёт sector.inside (DPC стр. 21–22) | Не давать DPC второй путь продаж. Перед зависимой реализацией явно согласовать исправление плана или обоснованную адаптацию |
| DPC 1 — касовые/партнёрские брони | Очередь `/v1/scans`, проверка билета 100–500 мс, sector invariant | Сохранить владельца лабораторной, уточнить предметную часть |
| DPC 2 — спрос/динамическая цена | `lambda(t)=A*t*exp(-t/tau)`, интеграл числа проходов | Использовать точную функцию карточки, не подменять бизнес-моделью |
| DPC 3 — эффекты бронирования | Эффект погашения по **ticket_id**, не scan_id | Разные scan одного ticket не создают второго прохода/эффекта |
| DPC 4 — выручка/заполненность, 80% hot concert | Проходы и медиана прихода по event/gate, **60%** hot concert | Другое распределение можно исследовать дополнительно, но не выдавать его за карточку |
| DPC 5 — ticket-telemetry, продажи/проходы | **scans**, accepted=true, gate, fixed **1 минута** | Сохранить точные topic/показатель/окно либо явно документировать допустимую адаптацию имён |
| DPC 6 — снятие просроченных броней | Распределитель возвращённых заранее зарезервированных Web мест waitlist, fencing assignment | Не строить expiry cleaner вместо требуемой роли |
| Web 6 — промокод/сервисный сбор | Конкретное место ряд/номер, старому клиенту auto-assignment | Оставить изменение для ЛР6, не сделать его целиком в ЛР1 |
| Зал, QR и генератор билетов в симуляторе | Графический зал не требуется; симулятор только списывает, Web выпускает билет | UI/QR — возможное расширение, не обязательный объём |
| Полная очередь 429/503 на выбор | DPC О1.2 **429 + Retry-After**; 503 при drain — Д1.4 | Не смешивать причины ошибок |
| Все перечисленные функции лабораторной обязательны | Обязательна только пометка **Ядро** | Отдельно выбрать остальные О и Д |

Разбор не переписывает исходный план: он сохранён неизменённым.
Методички допускают адаптацию таблиц/URL с сохранением инвариантов и смысла;
замена входа на продажу или иного численного/аналитического задания не следует
из одного разрешения переименовывать таблицы.

## Требует решения до реализации соответствующей части

1. Имена четырёх участников и личная зона пользователя.
2. Подтверждение приведения предметного описания плана к карточкам C01
   при сохранении распределения номеров лабораторных.
3. Какие необязательные О и Д выполняем; сейчас список не утверждён.
4. Общая БД/Kafka и конкретная схема/система миграций; инфраструктура ещё раздельная.
5. Auth: cookie/opaque/JWT; service token проверки билета DPC.
6. A/tau/T, метод интегрирования, tolerances; единицы и определение медианы прихода.
7. Политика оплаты на границе expires_at/результат позднего внешнего списания;
   как запретить два успешных списания на hold при разных operation_id.
8. Идентификаторы ticket_id/code, performance_id/event.id, резервов и назначений.
9. Надёжный commit-order курсор notifications при выбранном О5.3.
10. Точные watermark/dedup horizon и тестовые наборы, не выводить watermark
    автоматически из примера 10-минутного запаздывания.

Эти вопросы не блокируют сохранение памяти и не являются просьбой
пользователю ответить на всё сейчас. Уточнять по мере зависимых задач.
