# Правила работы, доказательства и сдача

Источники: оба введения, стр. 3–6; общие правила ЛР; DPC стр. 17.

## Объём и защита

- Команда **2–4 человека**, тема уникальна в группе; C01 уже выбрана пользователем.
- Каждое задание один раз на проект, вклад каждого отражается в README.
- Шесть последовательных ЛР каждого курса развивают одну систему; ранее
  выполненные требования сохраняются. Один общий проект покрывает **ядро обоих**
  и отдельно выбранные расширения; **один финальный защита** после готовности обоих.
- «Основные О» не синоним «все обязательны». Только пометка **Ядро** — минимум.
- Преподаватель использует свой check по внешним интерфейсам, проверяет код,
  модель/клиент/эксперименты и задаёт вопросы каждому участнику.
- Готовые каркасы допустимы, но их происхождение/библиотеки и собственный вклад
  указываются. Наличие контейнера или TODO не является реализацией механизма.

## Запуск и организация

Одна команда из README запускает контейнерную систему в явно описанном окружении.
Указать Docker/Compose версии, CPU/RAM/порты, build/start, env defaults,
миграции, запуск клиентов и генераторов. Web-клиент только через nginx;
клиенты и генераторы вне Compose. Отдельные процессы в Docker-сети допустимы;
несколько физических машин — дополнительные Д6.4, а не условие каждого ядра.
SQL migrations/NNN_name.sql по порядку либо полноценная migration system.
Иные технологии допустимы при объяснении эквивалентных механизмов.

Целевая организация пользователя: `web/`, `dpc/`, `migrations/`, `experiments/`,
`results/`, `docs/`, root Compose/checks/.env.example/README. Внесение этой структуры
не означает реализацию лабораторных. Не писать фиктивные результаты в results.

## Девять разделов итогового README

1. Курс и тема, команда.
2. Назначение системы, роли, операции, состояния, инварианты; для DPC также расчёт, batch и stream.
3. Компоненты/технологии, диаграмма и путь запроса/события.
4. Каталоги и ответственность модулей.
5. Требования к среде, build/start/config/migrations/clients/generators.
6. Каждая ЛР, **отдельно Web и DPC**: `пункт → реализация → проверка`.
7. Эксперименты: `опыт → режим/команда → данные → наблюдение/артефакт`.
8. Границы гарантий и controlled faults.
9. Вклад участников; готовые решения и зависимости отличить от своего кода.

Одна команда запускает подготовленные проверки выполненных пунктов. Демо-данные,
аккаунты и examples OpenAPI должны совпадать. Предметные маршруты обозначать
`x-course` либо явной mapping для check; актуальный checks.yaml — только фактические
реализованные/выбранные пункты, не желаемый список.

## Формат каждого опыта

Записать criterion/course, гипотезу/ожидание **до** опыта, commit/image,
CPU (физические ядра)/RAM/versions, исходные данные и seed/size/skew,
конфигурацию, точную команду, duration/concurrency/repeats, измеряемый интервал
и выборку, реальные результаты, invariant/reference comparison и ограничения.
Для percentile не подменять full completion HTTP latency. Не придумывать
числа из примера одногруппников и не выдавать их за наши измерения.

Сохранить сравнительные режимы **для выполненных пунктов**: unsafe vs protected,
старый клиент/сервер, local vs Ray, fencing off/on. Параметр запуска предпочтителен;
иначе указать commit/image и команду. Опасные режимы — отдельные тестовые данные.
Профиль/benchmark не доказывает гарантии вне исследованных отказов и нагрузок.

## Протокол аварий

`FAULTS=on` разрешает fault; файл **/faults/<name>** включает конкретную точку.
Процесс атомарно забирает одноразовый флаг, пишет **fault.hit**, немедленно
аварийно завершается **без graceful shutdown**. Несколько процессов не должны
сработать на один флаг многократно. В README: точка, команда, лог, reset состояния.
Обычный stop контейнера и pause координатора выполняются отдельно от fault-файлов.

| Курс / пункт | Точка / действие | Доказательство |
|---|---|---|
| Web О2.3 | after_commit_before_response | Retry другого экземпляра, прежний ответ, один эффект |
| Web О4.4 | publisher_before_send | Outbox переживает сбой, затем публикуется |
| Web О4.4 | after_external_before_commit | Одно списание через /effects и одно уведомление |
| Web О5.3 | stop gateway | Reconnect/catch-up без дыр/дублей |
| Web О6.3/О6.4 | SIGTERM под нагрузкой | Drain, ack только commit, порог ошибок выбранного опыта |
| DPC Д1.4 | SIGTERM при полной очереди | Все принятые завершены, новые 503 |
| DPC О3.4 | after_effect_before_ack | Ray retry, один ticket effect |
| DPC О4.5 | kill Spark executor | Итог совпадает с независимым эталоном |
| DPC О5.4 | kill stream | Тот же checkpoint, тот же итог, нет повторной записи |
| DPC О6.3 | pause A >TTL, B register, resume A | Старое поколение отвергается на ресурсе; unsafe control нарушает инвариант |

Не все строки этой таблицы обязательны: смотреть ядро и выбранные О/Д.
